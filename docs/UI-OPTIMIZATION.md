# 界面优化：需求 → 实现 → 验收

> 对应《指代器界面优化需求文档》的 R1–R5。每条都写明"怎么做的""怎么验的"，
> 以及**哪些是自动验证过的、哪些还需要你在浏览器里确认**。

## 一句话总结

优化前界面通篇是开发者语言（`p.lede`、`section.hero`、`html.z-picking > body > main > …`）；
优化后所有面向用户的地方统一说人话：**「橙色按钮「预约到店」」「简介文字「每周从 3 个产区空运…」」
「首屏大区块」「整个页面」**，代码信息一律降级到 tooltip / 折叠区，绝不删除。

## R1 元素命名"说人话"【P0】

**实现**：新增 `src/naming.mjs` —— 一个**统一纯函数翻译层**，唯一入口
`element → describeElement(el, {win, names, box, selectorPath}) → {name, icon, role, kind, isCustom, tooltip}`。

内部结构刻意分两层，便于测试与复用：

| 层 | 内容 | 是否碰 DOM |
| --- | --- | --- |
| 纯函数层 | `roleOf` / `colorName` / `smartTruncate` / `cleanText` / `composeName`（`describeFromFacts`）/ `chipsFor` / `breadcrumbFromChain` | 否，可直接单测 |
| DOM 适配层 | `describeElement` 只负责"取事实"：标签、类名、文本、computed 样式、位置、尺寸 | 是 |

命名规则（按优先级）：
1. 用户自定义名（R5）——最高优先；
2. class 关键词：`hero→首屏`、`lede→简介文字`、`btn→按钮`、`card→卡片`、`badge→标签`、`nav→导航`… 未命中的 class **忽略不显示**；
3. 标签角色：`h1→标题`、`p→文字`、`button→按钮`、`img→图片`、`ul→列表`、`section→区块`、`main/body/html→整个页面`；
4. 视觉特征：从 computed style 取主色（`橙色按钮`）；白底/透明底/灰字**不写颜色**（避免"白色卡片"这种噪音）；
5. 尺寸特征：宽度 ≥ 视口 70% 的容器加"大"字（`首屏区块 → 首屏大区块`）；
6. 位置特征：在 `header/nav` 内 → `顶部…`；在 `footer` 内 → `页脚…`；
7. 文本：文本类元素用自己的文本（截断 8~12 字）；容器优先用内部一句代表性的话（贺卡卡片 → `卡片「耶加雪菲 沃卡」`）；
8. **兜底**：翻译不出来时给"这一块区域/一块区域"这类通用名，**绝不回退展示选择器**（有测试守着）。

**复用（R1.5 硬要求）**：弹层、面包屑、右侧面板、发给 AI 的上下文**全部来自同一次 `describeElement` 调用**：

- 弹层：`picker.describe()` 带上 `name/icon/kind/tooltip`；
- 面包屑：`app.renderBreadcrumb(chain)` 用 `breadcrumbFromChain`（最多 3 级，中间折叠为「…」）；
- 面板：`ChatPanel.renderSelection()` 用 `name` 做主标题；
- AI 上下文：`selector.mjs` 的 `target.humanName` 与 `chain[].humanName`，系统提示词里明确告诉模型这个名字的含义。

**验收**：

- `node tools/test-naming.mjs` → **16 项**（R1.1 段落/按钮/hero/main、R1.2 截断与视觉特征、R1.3 tooltip 保留技术信息、R1.4 面包屑、R1.5 自定义名优先、降级安全、颜色归一）
- `node tools/test-app-wiring.mjs` → `R1`、`R1.4` 两项（真实 EditorApp 链路）
- 页面内自检 → `R1 …`、`R1.3 …` 两项
- 需你在浏览器确认：观感是否符合"零代码用户一眼看懂"（文案微调类需求只能靠人看）

## 用户反馈后的两个修复（第二轮）

### 修复 1：工作区不撑满视口，底部一大片白边

**根因**：让应用撑满视口的那条 CSS 写成了 `body.z-app { display:grid; height:100% }`，
但挂载点是 `<div id="app" class="z-app">`，**不是 `<body>`** —— 这条规则从未生效，
根容器高度由内容决定，于是预览区只占上半屏。

**修法**：改成类选择器 `.z-app`，并给出明确高度：

```css
.z-app { display: grid; grid-template-rows: 46px minmax(0, 1fr); height: 100dvh; overflow: hidden; }
```

同时给 `.z-main` 补 `height: 100%; overflow: hidden`，让内部滚动条不会把布局顶开。

**回归测试**：`test-bundle.mjs` 的「产物样式：应用根容器必须撑满视口」——
断言 `.z-app` 含 `height:100vh/100dvh`、含 `display:grid`、
且**不允许**出现"只挂在 `body.z-app` 上的布局规则"（就是这次踩的坑）。

### 修复 2：松手后选择界面完全消失，「让 AI 改这块」点不到（主功能不可用）

**根因**：`pointerdown` 弹层 → `pointerup` 立刻"选中 + 关闭弹层"。
弹层就贴在光标旁边，用户松手时根本来不及移上去点按钮，等于功能被吞掉。

**修法**（正是需求里建议的两种做法都做了）：

1. **松手 = 选中 + 弹层留在页面上**，变成"已选中工具条"（`.z-bubble.stuck`）：
   锚定到选中元素下方，贴边自动翻转；提示文案变成「已选中 / ↑↓ 换层级 / Esc 关闭」，
   并补一个 `✕` 关闭按钮；`让 AI 改这块 / ✎ 改名 / 复制选择器` 全部可点。
2. **按住时把指针移到弹层上 → 立即"钉住"**：不再跟随指针换层级，用户可以稳定点某一层或某个按钮。

**收起时机**：点 `✕` / 按 `Esc` / 点某个功能按钮（AI、改名、复制）/ 在页面上重新按住（替换成新的一个）。
页面上**同时只允许存在一个**工具条。

**顺带修掉的一个隐蔽 bug**：`select()` 内部会先 `clearSelection()` 并发出 `deselect`，
而应用在 `deselect` 里也关了弹层 —— 结果是"**第一次选中正常，第二次按住选中时工具条立刻被自己关掉**"。
现在 `deselect` 不再碰工具条，用户主动"取消选中"才走 `app.clearSelection()` 收起它。

**回归测试**：`test-app-wiring.mjs` 三项——
「按住弹出 → 松开后选择界面必须留下，并且能点到「让 AI 改这块」」、
「工具条状态下的 Esc 与"再按一次"都能收起它」、「按住时把指针移到选择界面上，弹层要"钉住"不乱动」；
另有页面内自检的「按住弹出 → 松开后选择界面留下，能点到「让 AI 改这块」」一项。

> 测试基础设施也顺手修了一个失真点：`dom-shim` 的 `dispatchEvent` 不支持冒泡、
> `dataset` 是只吞不存的 Proxy —— 前者导致"点按钮"模拟不出来，后者让 `dataset.x = y` 静默失效。

## 第三轮：解决"改动越界"（用户实际卡住的地方）

**用户视角**：他只是选中一块、说了一句很正常的需求
（「我希望这段文字下面有垫色块，字体和色块颜色对比明显」），
结果右侧弹出一句"改动越界：setStyle 想改 p-03f5c254，但它不在当前选中元素范围内"。
**这不是提示文案问题，是设计缺陷** —— 用户没做错任何事，也不该需要理解 pid 和范围。

### 根因（三个层次）

| 层次 | 问题 |
| --- | --- |
| 诱因 | `buildContext` 把**祖先元素的 pid** 也发给了模型。模型看到"加垫色块"这类需求，很自然会想改外层容器，于是引用祖先 pid → 必然越界。**等于我主动递了一把用不了的钥匙。** |
| 处理 | 越界是**硬拒绝**，没有任何自动纠正；用户看到错误就卡死在这里。 |
| 体验 | 错误里全是 pid 和 op 名，用户既看不懂也没有下一步可做。 |

### 修法（预防 → 自愈 → 出路）

**① 预防：不再提供"用不了的 pid"**
- 祖先元素只给 `ref`（`ancestor-2`…）并标注 `modifiable: false`，**不给 pid**；
- 新增 `target.modifiablePids`：明确列出可以改的 pid（选中元素自身 + 它内部元素）；
- 系统提示词加了两条硬规则：只能用白名单里的 pid；**需求超出选中范围时，不要报错也不要越界，
  而是用选中元素自身能实现的方式满足它**（例如"这段文字下面加垫色块" → 给标题自己设
  `background-color` + `padding` + 对比 `color`，这正是用户想要的效果）。

**② 自愈：真的越界时自动纠正一次**
`app.send()` 里加了重试循环：`applyPatch` 若返回 `E_PATCH_OUT_OF_SCOPE` / `E_PATCH_TARGET_MISSING`，
就把「被拒原因 + 可用 pid 白名单」回喂给模型重新生成，并在对话区说明"AI 想改的那块不在范围内，已让它改用选中元素自身实现"。

**③ 出路：自愈仍失败时给一键动作**
弹出可操作卡片：**「改选外层容器「大区块」并重试」** —— 点一下自动选中外层、用同样的需求重发；
旁边还有提示"或者把需求说得更具体（例如'给这个标题加背景色'）"。

### 真模型实测（本机跑过，用你给的硅基流动端点 + DeepSeek-V4-Flash）

同一条需求「我希望这段文字下面有垫色块，字体和色块颜色对比明显」，两个场景：

| 选中对象 | 修复前 | 修复后 |
| --- | --- | --- |
| 标题 h2「我们怎么烘豆」 | 引用祖先 pid → 整单被拒 | ✅ 4 条 `setStyle` 全部打在选中元素自身（深色垫块 + 浅色文字 + 内边距 + 圆角） |
| 表格单元格「方案/200g」（你截图里的场景） | 引用 `p-03f5c254`（范围外）→ 被拒 | ✅ 3 条 `setStyle` 全部打在选中单元格自身 |

上下文侧也验证了：`链上祖先是否还带 pid: false`，`可改 pid 白名单` 精确到选中元素及其内部元素。

### 回归测试

- `test-dom-smoke.mjs`：「上下文不再把"用不了的 pid"递给模型（越界的根因）」、
  「重试上下文会把"可改 pid 白名单 + 被拒原因"带上（自愈所需）」；
- `test-app-wiring.mjs`：「越界自愈：把"可改 pid 白名单"回喂模型并自动重新生成」、
  「越界且自愈仍失败时，给出"改选外层容器重试"的出路」；
- 页面内自检：「越界时会自动纠正，而不是让用户撞墙」。

## 第四轮：按住时的"高亮归谁驱动"

**用户反馈**：按住鼠标弹出候选界面后，本该"在这个列表里找附近可改的元素"，
但高亮仍然跟着**页面**（指针下面的元素）跑，滑到选项上也没用。

### 根因

`picker.onPointerMove` 在候选界面打开时，仍然用**页面命中测试**推算层级
（`chain.findIndex(指针在哪个元素范围内)`）并下发 `bubble-move`。
于是指针在页面上一动，高亮就跟着页面元素跳 —— 用户想伸手够选项的那段路，层级已经被改了好几次。

### 修法

1. **按住期间，层级完全由选择界面驱动**：`onPointerMove` 在候选界面打开时直接返回，
   不再用页面位置改层级；滑到哪个选项就高亮哪个（由弹层的 `mouseover` 处理）。
2. **把选中的层级回传给 iframe**（这条一开始漏了，被测试抓到）：
   真正在"松手"时执行选中动作的是 iframe 里的 picker，所以父窗口每次切换高亮
   都要通过新增的 `setBubbleIndex` RPC 把 index 同步回去，否则松手选中的还是最初那一层。
3. 提示文案区分状态：按住时显示「滑到某项即高亮 / ↑↓ 换层级 / 松开确定」，
   真正松手后才变成「已选中 / ↑↓ 换层级 / Esc 关闭」；在弹层上松手时由父窗口自己补记"已释放"
   （iframe 收不到弹层上的事件）。

**保持不变**：按下去之前，悬停仍然跟随页面（"鼠标移到哪就提示在选哪里"）——这是用户明确说好的部分。

### 回归测试

- `test-app-wiring.mjs`：「按住时层级由选择界面驱动，不跟随页面元素乱跳」——
  断言"页面移动后层级不变"、"滑到第 2 项后层级=1 且该项高亮"、"预览高亮换成第 2 项的名字"、
  "松手确定的就是高亮的那一层"；
- 页面内自检：「按住时高亮由选择界面驱动，不跟随页面乱跳」。

### 第四轮的两次误判与最终根因

用户反馈"按住时滑到选项上没反应，只有松手后才正常"。前两次都改错了地方：

| 尝试 | 改了什么 | 结果 |
| --- | --- | --- |
| 1 | 让"层级由选择界面驱动"，不再按页面命中测试 | 方向对，但没解决"按住时滑动无反应" |
| 2 | 发现"指针碰到弹层就钉住"会顺手把它挪到元素右下角 → 用户刚碰到就被弹走；改为按住期间保持原位 | 这确实是个真 bug，但**仍不是**用户卡住的原因 |
| 3 | **真正的根因：两层浏览器行为叠加** | ✅ 解决 |

**根因 A：兼容鼠标事件被抑制。**
指代器在 `pointerdown` 里调了 `preventDefault()`（防止按住拖拽时选中文字）。
按 Pointer Events 规范，**被取消的 `pointerdown` 会让该指针序列的兼容鼠标事件
（`mouseover` / `mouseup` / `click` …）全部不再触发**。
于是挂在弹层上的 `mouseover` 在按住期间根本收不到 —— 松手后新序列才开始正常工作，
这与用户观察到的现象**完全一致**。

**根因 B：跨 frame 拖拽的指针捕获。**
在 iframe 里按下、再把指针拖到 iframe 外面（即弹层上）时，Chrome 会把指针事件
**继续投递给 iframe**，父窗口连自己的 `pointerover` 也收不到。

**修法：双通道，任何一条通就生效**

- **通道 A（父窗口侧）**：弹层行的监听从 `mouseover` 改为**以 `pointerover` 为主**，
  释放用 **`pointerup` 为主**（pointer 事件不受 `preventDefault` 抑制），`mouseover/mouseup` 保留作兜底；
- **通道 B（iframe 坐标回传）**：按住期间 iframe 继续上报指针坐标（`bubble-pointer`），
  父窗口用 `Overlay.hoverAtPoint()` 把坐标换算到覆盖层坐标系、自己命中测试选项行 ——
  这条专治"事件被 iframe 捕获、父窗口收不到 hover"；
- 顺带把注入的瞄准样式加上 `user-select: none`。

**保持不变**：按下去之前，悬停仍跟随页面（"鼠标移到哪就提示在选哪里"）。

### 回归测试（都刻意只走"按住时真实可达"的通道）

- `test-app-wiring.mjs`「按住时把指针移到选择界面上：弹层不位移，滑到哪一项就高亮哪一项」——
  **只派发 `pointerover`**（不派发 `mouseover`），断言层级与高亮同步跟随、不同选项预览高亮不同、
  鼠标离开预览区不覆盖选项高亮、**只派发 `pointerup`** 也能在弹层上确认选中；
- `test-app-wiring.mjs`「按住时即使 iframe 捕获了指针事件，滑到选项上也要高亮（坐标回传通道）」——
  显式给出布局矩形，**只在 iframe 上派发 `pointermove`**，断言父窗口按坐标命中到正确的选项、
  并把层级同步回 iframe 里的 picker；
- 页面内自检「按住时滑到选项上就高亮（走真实浏览器路径）」——同样只派发 iframe 上的 `pointermove`，
  用真实布局矩形换算坐标。

优化过程中被测试抓出的真问题（都已修）：
1. `setAiming` 下发 `setMode` → 桥回发 `mode` 事件 → 又触发 `setAiming` → **无限 RPC 循环**（页面卡死）；
2. `loadWorkspace` 启动时的 `setMode` 与用户启动瞬间的操作**抢时序**，导致"关闭指代器"可能被覆盖回开启
   （改成：桥默认即 pick 模式，应用只同步视觉，不重复下发）；
3. 应用根容器的布局规则挂在 `body.z-app` 上**从未生效** → 底部一大片白边；
4. `deselect` 事件把工具条关掉 → **第二次按住选中时选择界面立刻消失**；
5. shim 的 `dispatchEvent` 不冒泡 / `dataset` 只吞不存 → 让"点按钮"与属性写入在测试里失真。
