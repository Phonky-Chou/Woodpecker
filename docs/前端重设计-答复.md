## 0. 判据：确认一致，并给你一个结构性好消息

> **核心功能只有一个：鼠标选哪、就改哪。** 其余一切设计都服务于这个动作。

**完全一致**，这就是原始设计意图。补充三点，其中第一点对你是好消息：

1. **"选哪/改哪"的最强视觉信号画在父窗口的覆盖层上，不在 iframe 里。**
   高亮框（`.z-hl-tag`）、环绕泡泡（`.z-bubble`）、暗角（`.z-vignette`）、跟随光标的人话名（`.z-cursor-tip`）

2. **暗角压的是"展厅"（用户页面），不是"外壳"。** 压暗页面让高亮框成为第一信号 —— 与"外壳退后"不冲突。

### 4.2 `z-` 前缀是命名习惯还是隔离契约？

**是"约定"，但不是隔离的保证机制。** 真正的保证有三条：
1. 外壳 DOM 在**父窗口**，样式根本进不了 iframe；
2. 导出靠 `scrubEditorArtifacts`（`patch.mjs:122-148`）+ `sanitizeHtmlFragment`（`:63-77`）**按清单剥离**；
3. 命中测试与统计跳过 `data-z-chrome` 节点。

**含义（重要）**：清洗是**白名单式**的。你改了产生端却不改清理端，导出立刻变脏。
例如你把 `picker-selected` 改名成 `my-selected`，但 `patch.mjs` 的清单没改 → 导出的 HTML 里会留下 `my-selected`。
→ **动这些名字时，改的是"两处"**：产生处 + `EDITOR_CLASSES`（`patch.mjs:35-44`）。

| `picker-selected` / `z-preview-flash` / `z-ai-touched` | ❌ 不会 | `EDITOR_CLASSES`（`patch.mjs:35-44`，本轮扩充） |

| 新插入图片的 `data-z-asset` | ❌ 不会 | 该属性根本没被产出（`insertImage` 只产出 `<img src alt style>`，`patch.mjs:299-306`） |
| `data-asset`（父窗口缩略图卡） | ❌ 不会 | 只在父窗口 DOM（`ui.mjs:144`），永不进 iframe |

**结论**：你可以安全地重命名 🟢 类（对导出零影响）；重命名 🔴 标记**必须先改清理端**，否则导出立刻变脏。

## 8. Q8 命名引擎与 UI 的一致性约束

- **"一致"的判定边界**：同一个 pid 在 **①弹层 ②面包屑 ③右侧选区卡 ④AI 上下文** 里显示**同一个名字**，
  在同一会话内、同一时刻成立。**位置可以随意变**（左栏、下拉、状态栏都行），只要四处同源。
- **名字从哪来**：`src/naming.mjs` 的 `describeElement()`；四处都调它（或它的缓存）。
- **长度**：`smartTruncate(input, max=10)`（`naming.mjs`）；`util.mjs` 另有 `truncate(str, 120)`；CSS 侧靠 `text-overflow: ellipsis`。

- ⚠️ **不要改命名的"规则"**：`humanName` 会进 **AI 上下文**（`selector.mjs`），改规则=改模型的理解。
  改**展示**（位置/字号/省略/换色）完全没问题；改**词法**（比如把"橙色按钮「预约到店」"改成"按钮/预约到店"）

## 9. Q9 响应式与最小尺寸

- **现状**：只有一条 `@media (max-width: 1080px)`，把侧栏从 380px 缩到 330px（`app.css:498-500`）。

## 10. Q10 主题

- **为什么是单暗色**：是**产品决定**，不是"没做"——① 编辑工具类产品的惯例；② 用户页面多为亮色，
  暗色外壳能"退后"，让内容跳出来；③ 暗角机制需要一个比页面更暗的外壳才有意义。
- **`--z-*` token 体系能不能整体换肤？** —— **不能，只覆盖骨架。** 实测（`src/app.css`）：
  - 定义 **16 个 token**，`var(--z-*)` 用了 **128 处**；
  - 但正文里还有 **113 处硬编码 hex（66 个不同值）+ 21 处 rgba（18 个不同值）**，分布在 **89/202 条规则**里。
  - 重灾区：`.z-cursor-tip`(3)、`.z-bubble-chain button.on`(3)、`.z-sel-tag`(3)、`.z-sel-preview`(3)、
    `.z-tech-row code`(3)、`.z-msg.err .z-msg-body`(3)、`.z-raw`(3)、`.z-card`(3)、`.z-card.accepted`(3)、
    `.z-code`(3)、`.z-btn:hover`(2)、`.z-btn.danger`(2)。
  - 另有 **JS 里的内联样式**：`ui.mjs` 11 处 `style="…"`、`overlay.mjs` 2 处 + 11 处 `.style.x=`、
    `selftest.mjs` 6 处、`app.mjs` 1 处。→ 你改视觉时**不能只改 CSS**，有些标签在 `ui.mjs` 的模板串里。
- **所以**：
  1. 若只做**一个**新外观 → 直接改 CSS + 那些内联样式即可，不必先做 token 化；
  2. 若要做**多套主题/亮色** → 建议先做一次"token 化机械重构"（把 84 个字面量收敛成 ~20 个**语义 token**：
     `--z-ok-bg/--z-ok-fg/--z-danger-bg/--z-danger-fg/--z-code-bg/--z-hover-bg/--z-badge-*`…），
     再做主题切换。这一步**不改任何行为**，我可以先做（或你做完我审）。
- **亮色主题不算超范围**，但有一条硬要求：亮色下 `.z-vignette`（暗角）与高亮框的对比关系要重算，
  否则"选哪"会从第一信号掉到第二信号 —— 那就违反第 0 节判据了。

## 11. Q11 七条历史决定的理由（含两条"其实是顺手"）

| # | 问题 | 理由（诚实版） |
| --- | --- | --- |
| 1 | 顶栏 46px 单行 | **信息量决定的**：顶栏只放"全局动作"，上下文相关动作都在工具条/右侧。46px ≈ 一行 12.5px 文字 + 9px 上下内边距。**不是神圣数字**，可以改；但别变两行——那会永久压缩舞台高度（舞台是主角） |
| 2 | 侧栏固定宽、在右 | **左"展厅"右"操作台"**：右侧更贴近"选中后说需求"的动线（左→右），且不遮挡页面本身；固定宽是为了舞台尺寸稳定（内容不跳）。**可以改成可拖拽**（Q9 已确认安全）。放在**左侧**也可以，但要注意面包屑/选中卡与页面的阅读顺序 |
| 3 | 改动预览是卡片列表而非 diff | **目标用户是零代码用户**：diff 的行号与 `+/-` 对他们没有判断价值。判定依据是"用户能否在不理解代码的前提下决定接受或取消"。所以卡片给的是**人话摘要 + 属性级变化**（`font-size: 32px → 44px`）。**如果你能证明某种可视化比这个更容易判断，我支持换** |
| 4 | 代码信息降级到 tooltip + 折叠区 | 同一判据（零代码用户）。**但不是删除**——这是 R1.3 的硬要求：技术信息必须仍可查（开发者要用）。所以设计上要保留一个"可展开的技术区" |
| 5 | 工具条"钉住"而不是松手即走 | **被真实用户反馈逼出来的**，不是审美：弹层贴在光标旁，松手即走 → 用户来不及移上去点"让 AI 改这块"，主功能等于不可用。**别改回"松手即走"** |
| 6 | 隔离用两层（隔离层 + window 捕获守卫） | 单层不够：只拦事件挡不住"页面把监听挂在 `document/window` 捕获阶段"，也挡不住 CSS `:hover`（CSS 不受 JS 阻止影响）；只铺隔离层挡不住冒泡到 window 的监听。**视觉上目前几乎没有提示**（只有光标变准星 + 药丸 + 状态条一行字）→ **强烈建议你设计一个"页面已冻结"的可见提示**，这是我的遗漏 |
| 7 | 暗角为什么要有 | 压低页面对比度，让高亮框成为第一信号；压的是**页面**（展厅熄灯），不是外壳。它属于 overlay（父窗口），改外壳不影响它。**与"外壳退后"不冲突**——但亮色主题下要重算（见 Q10） |

## 16. Q16 交付方式

1. **先出静态设计稿**（我的建议）：2–3 个方案，各自一个**独立单文件 HTML**（可直接双击、自带假数据或真实截图），
   让用户选方向。理由：视觉靠肉眼最快，且不必反复重建产物、不必反复跑测试。
2. **设计稿放哪**：`design/<方案名>/`，规则：
   - **进 git**（便于对比与迭代），但加 `design/README.md` 说明"这不是产物、不参与构建、不会被 `build.mjs` 打包"；
   - **不要**放进 `out/`（那是产物目录，且 build 不会清理它，容易混淆）。
3. **分支**：每个方案一支 `design/<slug>`；落地支 `feat/ui-redesign-<slug>`。
4. **commit 风格**：沿用现有的 —— `feat(ui): …` / `style(ui): …` / `docs: …` / `fix(指代器): …`；
   一次提交只做一件事；**落地提交必须同时包含重建后的 `out/` 三个产物**。
5. **PR 描述**里给"before/after 对照"+ 逐项说明你改了哪些 🟢/🟡 标识符、同步改了哪些测试。
